# 「오피스 한국어 코치」 웹앱 확장 명세

## 0. 목표
현재의 "직장 한국어 연습 도우미"(표현 소개 → 빈칸 퀴즈 → 채점)를 그대로 유지하면서, 아래 3가지 기능을 더해 「오피스 한국어 코치」 웹앱으로 확장한다.
① 상황 롤플레이: 장면 카드를 고르면 AI가 상사·동료·거래처 역할로 대화를 이어 가고, 대화가 끝나면 피드백을 준다.
② 이메일 첨삭: 받는 사람과 목적에 비추어 높임법·완곡 표현·결론 먼저 쓰기를 점검하고, 고친 예시를 보여 준다.
③ 나의 표현 노트: ①②에서 지적받은 표현과 고친 표현을 모아 복습 카드로 만들고, 정해진 간격으로 다시 퀴즈를 낸다.

대상: 한국 기업 취업을 준비하는 외국인 학습자(초급·중급·고급), 입사 초기 외국인 직장인
학습 목표: 문법 정확성보다, 상대(상사·동료·거래처)와 상황에 맞는 표현 선택(높임법, 완곡 표현, 보고 순서)을 스스로 점검하게 하는 것

## 2. 바꾸지 말아야 할 것 (제약 조건)
1. API 키 처리 방식(서버에서 process.env.OPENAI_API_KEY 사용, .env.local)은 그대로 둔다. 키를 프런트엔드로 보내거나 NEXT_PUBLIC_/VITE_ 접두사 변수로 바꾸지 않는다.
2. 모델명, reasoning 설정, 스트리밍(SSE) 응답 방식은 그대로 둔다.
3. 표현 연습의 3단계 구조(표현 소개 → 빈칸 퀴즈 → 채점)와 난이도별 언어 규칙(초급만 영어 병기)은 유지한다. (WORKPLACE_KOREAN_SYSTEM_PROMPT는 11장 '표현 연습 확장'에 따라 개정됨)
4. 엔드포인트는 /api/chat 하나만 쓴다(vite.config.ts 개발 플러그인이 /api/chat만 연결함).
5. 기존 UI 스타일(색상, 버튼 모양, 말풍선, 오류 배너)을 재사용한다.
6. 새 라이브러리(라우터, 상태관리, UI 키트 등)는 설치하지 않는다. 탭 전환은 React state로 구현한다.
7. 서버·DB는 추가하지 않는다. 표현 노트는 브라우저 localStorage에 저장한다.

## 3. 전체 화면 구조
- 헤더 제목: "💼 오피스 한국어 코치", 부제: "보고·회의·이메일 장면에서 대화하고, 쓰고, 피드백 받는 직장 한국어 연습"
- 탭 4개: [표현 연습] [상황 롤플레이] [이메일 첨삭] [나의 표현 노트 ●N] (●N = 오늘 복습할 카드 수, 0이면 숨김)
- 탭을 바꿔도 각 탭의 대화 내용과 입력 상태는 유지한다.
- 스트리밍 중에는 탭 전환 버튼을 비활성화한다.
- 헤더의 "대화 초기화" 버튼은 현재 탭만 초기화한다.
- 375px(모바일) 폭에서도 탭과 입력창이 깨지지 않는다.
- 서버 전용 프롬프트·장면 데이터는 api/_lib/에 둔다(밑줄: Vercel이 별도 함수로 배포하지 않음). import는 './_lib/prompts.js'처럼 .js 확장자를 붙인다. src와 api 사이에는 서로 import하지 않는다.

## 4. API
1. 요청 본문: { mode, sceneId?, messages, level?, supportType?, frameTemplate?, simplify? } (simplify는 초급 roleplay 전용, 13-1) — mode: 'expression' | 'roleplay' | 'email' | 'review' | 'roleplay_support', 없으면 'expression'. level·supportType은 roleplay_support 전용(13장).
2. mode 허용 목록 검사, 아니면 400.
3. mode별 instructions: expression=기존 프롬프트 / roleplay=공통 프롬프트+서버 장면 설정(sceneId 없거나 목록에 없으면 400) / email=EMAIL_COACH / review=REVIEW_GRADER
4. 장면 설정과 시스템 프롬프트는 서버에서만 조립한다. 클라이언트 텍스트를 instructions에 넣지 않는다.
5. messages 1~40개, 각 메시지는 role이 user·assistant, content가 문자열, 최대 4,000자. roleplay_support 외 모드는 마지막 메시지가 user여야 함. 어기면 400 + 한국어 오류 메시지.
6. streamChatMessage(messages, onDelta, options?)에 { mode?, sceneId? } 추가, 기존 호출부 호환.

## 5. 응답 끝 메타 블록 규약
- 노트용: [[NOTES]] JSON 배열 [[/NOTES]] — 항목 필드: scene, counterpart, original, corrected, category("높임법"|"완곡 표현"|"보고 순서"|"어휘·문법"), reason. 고칠 표현이 없으면 []. 코드 펜스 없이 JSON만.
- 채점용: [[RESULT]]{"verdict":"alternative","correct":true}[[/RESULT]] — verdict: "correct" | "alternative" | "partial" | "incorrect". correct는 verdict가 correct·alternative이면 true(하위 호환). verdict가 없으면 correct 값으로 판단한다.
- 복습 채점은 판정과 상관없이 마지막 줄에 [[RESULT]]를 반드시 붙인다. 블록이 없거나 잘못됐으면 클라이언트가 "결과:" 줄로 판정을 대신 읽고 console.warn으로 남긴다(긴 문구부터 확인: "✅ 정답(다른 적절한 표현)" → alternative, "🟡 부분 정답" → partial, "❌ 오답" → incorrect, "✅ 정답" → correct). 그래도 못 읽으면 자기 채점으로 전환한다.
- 표현 연습 채점도 🟡 부분 정답·❌ 오답일 때만 [[NOTES]] 1개를 붙인다(11장).
- 화면 표시 시 마커부터 끝까지 숨김. 스트리밍 중 마커 일부("[[NO" 등)로 끝나는 꼬리도 숨김.
- 스트리밍 종료 후 JSON.parse + 필드 검증. 실패하면 저장 버튼을 보여 주지 않고 조용히 넘어감.
- 대화 기록을 다시 보낼 때도 메타 블록 제거.

## 6. 상황 롤플레이
### 흐름
1. 장면 카드 그리드(제목, 상대, 한 줄 상황, 연습 목표)
2. 카드 선택 → [초급] [중급] [고급] + "← 장면 다시 선택" (초급은 장면 데이터의 openingLineBeginner를 첫 대사로 씀, 13장)
3. 난이도 선택 → "장면 · 상대 · 목표" 요약 바 고정, 첫 대사를 장면 데이터에서 즉시 표시(API 호출 없이 assistant 메시지로 기록)
4. 학습자 입력 → mode:'roleplay', sceneId, level 전송. 난이도는 대화 기록에 붙이지 않고 서버가 level(화이트리스트, 없거나 잘못되면 400)을 검증해 instructions의 "이번 대화 난이도"로 넣음. 이전 버전이 남긴 "[난이도: …]" 표시는 화면 표시·API 전송 직전(meta.ts stripLevelTag)과 서버에서 지움
5. [피드백 받기] 버튼 → "[피드백 요청] 대화를 마치고 피드백을 주세요." 전송
6. 피드백 후 NOTES 체크박스 목록(기본 전체 선택) + [선택한 표현 노트에 저장], 저장 후 "표현 노트에 N개 저장했어요". 자동 저장 금지.
### 장면 (id / 제목 / 상대 / 상황 / 목표 / 첫 대사) — 회사·인물은 가상
- 장면 문구도 난이도 기준을 따름: 금지 어휘('분기') 제거, 초급 첫 대사·초급 상황(situationBeginner)은 한자어 명사 겹침 없이 씀
1. report-delay / 일정 지연 보고 / 김 팀장(직속 상사) / 금요일까지 내기로 한 시장 조사 보고서가 자료 수집 지연으로 다음 주 화요일로 늦어질 것 같음 / 결론(지연) → 원인 → 대책·새 일정 / "지금 잠깐 괜찮아요? 지난주에 맡긴 시장 조사 보고서는 어떻게 되고 있어요?"
2. report-progress / 업무 중간보고 / 김 팀장 / 행사 준비 약 70% 진행, 장소 계약에 문제 하나(초급: '행사 일이 70% 끝났음. 장소에 문제가 하나 있음') / 핵심 먼저, 수치로 짧게 / "이번 행사 준비 진행 상황 좀 간단히 말해 줄래요?" (초급: "행사는 어떻게 돼요? 준비 많이 했어요?")
3. meeting-disagree / 회의에서 반대 의견 부드럽게 말하기 / 박 과장(회의 진행자) / SNS 광고로만 홍보하자는 제안에 예산·주 고객층 문제로 다른 의견 / 상대 의견 인정 → 완곡한 반대 → 근거 → 대안 / "그럼 이번 홍보는 SNS 광고로만 진행하는 걸로 정리할게요. 다른 의견 있으세요?"
4. meeting-schedule / 회의 일정 조율 / 이 대리(다른 팀 동료) / 목요일 오후 회의에 출장으로 참석 어려움 / 사정 설명 + 대안 시간 제시 / "목요일 오후 2시 회의 초대 보냈는데 확인했어요?"
5. client-postpone / 거래처 미팅 연기 요청(전화) / 최 부장(거래처 한빛상사) / 내일 오전 미팅을 내부 사정으로 다음 주로 / 사과 → 간단한 사유 → 대안 일정 → 양해 구하기 / "네, 한빛상사 최민수입니다."
6. colleague-request / 다른 부서에 자료 협조 요청 / 정 대리(재무팀) / 다음 주 회의에 쓸 예산 자료 필요, 상대도 바쁜 시기 / 쿠션어 + 구체적 요청(무엇을, 언제까지) / "네, 재무팀 정하나입니다. 무슨 일이세요?"
### ROLEPLAY 프롬프트 요구사항
- 대화 중에는 상대역으로만 말한다. 한 번에 1~3문장, 사내 구어처럼. 중급은 짧고 쉽게, 고급은 실제에 가깝게.
- 연습 목표의 단계(원인, 새 일정, 대안 등)가 빠지면 역할 안에서 한 번에 하나씩 짧게 되묻는다(프롬프트 예시는 실제 장면 대사를 쓰지 않음).
- 대화 중에는 고쳐 주지 않는다. 못 알아들으면 "죄송한데, 다시 한번 말씀해 주시겠어요?"
- 학습자가 영어로 묻거나 도움을 청하면 "(도움말) …" 한 줄 후 역할로 복귀.
- 학습자 발화 8번 초과 시 자연스럽게 마무리 + "(대화를 마치려면 '피드백 받기' 버튼을 눌러 주세요.)"
- "[피드백 요청]"을 받으면 아래 형식으로만 피드백:
  ## 롤플레이 피드백 / **장면:** · **상대:** / ### 잘한 점(1~2개, 학습자 발화 인용) / ### 다시 생각해 볼 표현(최대 3개: 내가 한 말 / 더 알맞은 표현 / 이유: [범주] — 상대·상황 근거) / ### 말하기 순서 점검 / ### 다음에 써 볼 한 문장 / [[NOTES]]…[[/NOTES]]
- 지적하려면 원래 표현의 문제 부분(높임·완곡함·순서·문법)을 짚을 수 있어야 하며, 확실하지 않으면 지적하지 않는다. 이미 완곡한 말에 완곡 표현을 겹치게 하지 않는다. "더 알맞은 표현"이 원문과 같거나 이유가 칭찬이면 그 항목을 쓰지 않는다(화면도 원문과 고친 표현이 같은 NOTES 항목은 버림). 이미 알맞은 문장, 뜻·정중함이 같은 다른 문장으로 바꾸기만 하는 지적, 학습자 난이도 문체(중급 해요체 등)를 이유로 한 지적은 하지 않는다. 지적할 것이 없으면 "이번 대화에서는 고칠 표현이 없어요." 한 줄 + NOTES [].

## 7. 이메일 첨삭
### 흐름
1. 폼: 받는 사람(팀장(상사)/같은 팀 동료/다른 부서 동료/거래처 담당자/고객), 목적(요청/일정 변경·연기/사과/보고/감사/거절), 상황 메모(선택, 100자), 제목, 본문(필수, 2,000자, 글자 수 표시)
2. [첨삭 받기] → "[이메일 첨삭 요청]\n받는 사람: …\n목적: …\n상황 메모: …\n제목: …\n본문:\n…" 형식으로 mode:'email' 전송
3. 결과 아래에서 추가 질문 채팅 가능
4. NOTES 저장 UI(롤플레이와 동일)
5. [새 이메일 쓰기]로 폼 초기화
### EMAIL_COACH 프롬프트 요구사항
- 우선순위: 높임법 > 완곡 표현 > 결론 먼저 쓰기 > 문법(사소한 문법 오류는 최대 1개만 언급)
- 학습자 내용·의도 유지, 잘 쓴 부분은 바꾸지 않음
- 없는 사실(날짜·금액·이름)은 지어내지 않고 [날짜], [담당자명] 자리표시
- 거래처·고객은 하십시오체 기본, 사내 동료는 해요체 허용
- 본문이 너무 짧으면 더 써 달라고 안내, NOTES는 []
- 출력: ## 첨삭 결과 / **받는 사람:** · **목적:** / ### 한눈에 보기(높임법·완곡 표현·결론 먼저 쓰기 각각 ✅/⚠️/❌ + 한 줄) / ### 고칠 부분(최대 5개: 원문 / 고친 표현 / 이유: [범주] — 근거) / ### 고친 예시(제목+본문 전체, 고친 곳만 **굵게**, 고친 표현을 넣은 뒤 앞뒤 문장이 겹치거나 어색하면 함께 다듬음) / [[NOTES]]…[[/NOTES]]
- 난이도 정보가 없으므로 고친 표현은 공통 난이도 기준의 고급 기준(문체·어휘·금지 어휘)을 따른다.

## 9. 모든 AI 프롬프트 공통 피드백 원칙 (api/_lib/level-rules.ts EXPLANATION_PRINCIPLES 하나로 정의)
1. 근거는 상대·장면·목적으로 설명한다. "한국인은 원래…", "외국인은 보통…" 같은 국적·문화 범주 단정 금지.
2. 관례는 "이 상황에서 이렇게 말하면 더 정중하게 들린다/오해를 줄인다"처럼 사용 효과로 설명하고, 가치관 동의를 요구하지 않는다(이해·사용·동의 구분).
3. 문법보다 표현 선택(높임법·완곡 표현·보고 순서) 우선.
4. 칭찬은 구체적으로, 과장 금지.
5. 지적 개수 상한(롤플레이 3, 이메일 5).
6. 학습자 난이도에 맞는 쉬운 한국어(초급은 영어 병기).
7. 학습자가 말하지 않은 사실은 지어내지 않는다.

## 11. 표현 연습 확장 (문형·세트·명령어)
- 3단계 구조(표현 소개 → 빈칸 퀴즈 → 채점)와 난이도별 언어 규칙(초급은 힌트·안내·해설에 영어 병기, 중·고급은 한국어만)은 유지한다.
### 학습자 명령어
- "퀴즈 시작"/"퀴즈시작": 소개한 표현 중 아직 출제하지 않은 표현으로 빈칸 퀴즈 1개. 가장 최근 세트 우선. 모두 출제했으면 이미 낸 표현을 아직 쓰지 않은 문장(대표 문장·"더 보기" 문장 또는 같은 문형의 새 문장)으로.
- "다른 표현"/"표현 더 보기"/"다른 문형": 같은 주제·난이도에서 아직 나오지 않은 새 표현 3개를 1단계 형식으로. 제목에 세트 번호와 업종("1단계: 표현 소개 (세트 2 · 여행사)").
- 퀴즈 답을 기다리는 중에 명령어가 오면 명령어를 먼저 처리하고, 답하지 않은 퀴즈의 정답은 한 줄로 알려 준다.
- 중복 방지(코드 + 프롬프트): 화면(Chatbot.tsx, src/utils/expressionHistory.ts)이 표현 소개 응답마다 "문형:" 줄 값과 번호 붙은 대표 문장을 뽑아 누적한다. "다른 표현"/"퀴즈 시작"(버튼·직접 입력)을 보낼 때 화면에는 누른 문구만 보이고, API 전송용 사용자 메시지 끝에만 [이미 소개한 문형](쉼표 구분)·[이미 쓴 대표 문장](" / " 구분) 블록을 붙인다(각 최근 30개). 블록은 사용자 메시지(input)에만 넣고 instructions에는 넣지 않는다. 대화 기록은 표시용(content)과 전송용(apiContent)을 따로 저장하고, 다시 보낼 때 전송용을 쓴다. 대화 초기화나 주제·난이도 재선택 시 기록을 비운다.
- AI는 블록을 대화 기록보다 우선하는 기준으로 삼아, "다른 표현"에서 블록의 문형을 다시 고르지 않고, 블록의 대표 문장과 같거나 거의 같은 문장(조사·어미만 바꾼 것 포함)을 대표 문장·"더 보기" 어디에도 쓰지 않는다. 블록은 학습자에게 보이거나 언급되지 않는다.
- 목록을 다 썼을 때(같은 주제·난이도에 안 쓴 문형이 3개 미만): ① 같은 주제의 안 쓴 문형 → ② 같은 난이도 다른 주제의 안 쓴 문형(현재 장면에 맞게 새 대표 문장) → ③ 이미 소개한 문형을 새 대표 문장으로 복습(항목 제목 끝 "(복습)", 세트 제목 아래 안내 한 줄: "이 주제의 새 문형을 모두 배웠어요. 지금부터는 배운 문형을 새 문장으로 복습해요." 초급은 영어 병기).
- "퀴즈 시작"은 붙은 [이미 쓴 대표 문장]을 참고해 아직 퀴즈로 내지 않은 문형을 우선 출제한다.
- 첫 세트도 서버가 지정: 실제 응답 검증에서 모델이 첫 세트 문형을 다른 주제 목록에서 고르는 일이 반복되어, 주제·난이도 선택 때도 서버가 그 주제 목록의 앞 3개 문형을 지정한다(buildStartInstruction). 두 안내 끝에는 문장 품질 안내(품사에 맞는 활용, 같은 문형의 "더 보기", 목표 문형 밖 연결 어미 금지, 목적어–서술어 호응, 사용 장면과 시제 일치, 업종과 자기소개 소속 일치, [격식] 덩어리 표현의 만들기 방식)를 붙인다.
- 서버 지정(api/_lib/patterns.ts, api/chat.ts): 문형 목록은 patterns.ts의 데이터가 유일한 원본이고, 프롬프트의 목록 글은 이 데이터로 만든다. 표현 연습 모드에서 마지막 사용자 메시지가 "다른 표현"이면 서버가 블록의 [이미 소개한 문형]과 첫 메시지의 주제·난이도를 읽어 위 순서(같은 주제 → 같은 난이도 다른 주제 → 복습)로 다음 세트 문형 3개를 직접 골라 instructions 끝에 붙인다(표기가 달라도 같은 문형으로 보도록 정규화, 여러 목록에 있는 문형은 한 번만 셈). 첫 세트(주제·난이도 선택)에는 위 첫 세트 지정 문형과 어휘·형식·높임 안내를 붙인다. 두 안내 모두 그 난이도에서 쓸 수 있는 어휘(아래 단계 포함)와 쓰지 않을 위 단계 어휘, 명사 겹침 규칙(초급 금지, 중·고급 한 문장에 1개까지), 형식 안내(세 항목 모두 "· 더 보기:" 줄을 빼지 않음)를 함께 적는다(어휘 목록 원본은 level-rules.ts의 VOCAB, 프롬프트의 어휘 줄은 이 데이터로 만든다). instructions에는 서버 목록의 문형·어휘와 고정 문구만 들어가고 클라이언트 텍스트는 들어가지 않는다.
- 두 번 출력 안전장치: 응답 전체가 같은 내용으로 두 번 이어 붙어 오면(앞뒤 절반이 완전히 같을 때) 한 번만 남기고, 표현 소개 응답에 세트 제목("1단계: 표현 소개")이 두 번 이상 나오면(초안 + 고친 판) 마지막 판만 남긴다. 화면과 이후 대화 기록 모두에 적용하고 console.warn으로 기록한다(meta.ts collapseRepeatedReply, keepLastIntroSet).
- 출력 직전 자기 점검 문구는 초안과 고친 판을 둘 다 출력하게 만들어 제거했다. 형식("더 보기" 누락 방지)·어휘·높임 안내는 서버 안내 끝에 둔다.
### 표현 선택 원칙
- 3개는 의사소통 기능과 문형(어미·문법 구조)이 서로 겹치지 않게.
- 주제·난이도별 문형 목록(보고/이메일/회의 × 초급/중급/고급)에서 우선 고르고, 다 쓰면 그 난이도의 문법 범위 안에서만 다른 표현을 만든다. 목록은 『3주완성 연세 한국어』 기준(초급=1·2권, 중급=3권, 고급=4권 + [격식] 덩어리 표현, [보충] 표현. 2권 문법은 과 제목에서 추정해 [Y2-n·추정]으로 표시)이며, 전체 목록과 규칙은 docs/level-guide.md(교사용)에 있다. 실제 원문은 api/_lib/prompts.ts.
- 난이도별 문장 규칙(대표 문장·"더 보기"·퀴즈 문장 공통):
  · 길이: 초급 2~4어절(최대 5), 중급 3~6어절(최대 7), 고급 4~7어절(최대 8). 범위는 권장, 최대 어절은 필수(점검은 최대 어절 초과 여부만). 시각 표현(두 시, 오전 열 시, 세 시 반 등)은 띄어 써도 한 어절로 센다. '-(으)ㄹ 수 있다'·'-(으)ㄹ 수도 있다'(끝낼 수 있어요, 늦을 수도 있어요)와 '-고 있다'(정리하고 있어요)도 앞 동사와 함께, 'N 중이다'(확인 중입니다)도 앞 명사와 함께 한 어절로 센다. '-아/어 주다'(보내 주세요, 확인해 주시겠어요?)도 앞 동사와 함께 한 어절로 센다. 한 문장에 목표 문형 1개.
  · 어휘: 내용 명사 초급 2개·중급 3개·고급 3개 이하. 한자어 겹침 명사구는 초급 금지(단, 자기소개의 '회사·업종 + 직원'은 예외로 허용), 중·고급 1개까지. 단계별 직장 어휘 우선, 피해야 할 어휘(경쟁력, 협력사, 납품, 분기, 예산 초과, 재발, 차질, 파악되다)와 업계 전문 용어 금지. 위 단계 어휘 목록의 단어는 아래 단계에서 하나도 쓰지 않음(초급은 중급·고급 목록 전체, 중급은 고급 목록 전체 금지). 초급은 업종을 명사구(예: 제품 자료)로 드러내지 않고, 필요하면 업종 단어 하나만 단독으로.
  · 높임: 초급은 해요체 기본(하십시오체는 '-습니다' 평서형·고정 인사 표현만), 중급은 해요체 + '-겠습니다' 등, 고급은 상사·거래처에 하십시오체 + [격식] 표현.
  · 설명 줄: 기능은 문법 용어 없이 쉬운 한 문장(초급 영어 병기), 만들기 초급 1개·중·고급 2개, 주의는 중·고급에서 필요할 때만(초급 생략), 번역은 짧고 쉬운 영어.
- "-(으)ㅂ시다"(초급): 회의 진행자가 여러 사람에게 제안하는 장면에서만 소개하고, 사용 장면에 "회의를 진행할 때, 여러 사람에게"를 밝히며, 초급이지만 예외로 주의 줄(상사 한 사람에게는 무례할 수 있으니 "-(으)ㄹ까요?"를 쓴다, 영어 병기)을 넣는다. 초급 하십시오체 제한의 예외.
- 교재 예문은 옮기지 않고 같은 수준의 새 문장을 만든다. 교재 PDF는 프로젝트에 넣지 않는다.
- 한 세트의 대표 문장 3개(와 "더 보기" 문장)는 같은 회사 배경(업종) 하나로 통일하고, 그 업종을 세트 제목에 표시한다(예: "1단계: 표현 소개 (세트 2 · 여행사)").
- 다음 세트는 앞 세트 제목에서 쓰지 않은 업종을 고른다(여행사, 엔터테인먼트 회사, 화장품 회사, 전자 회사, 무역 회사, 병원 등).
- 업종은 제목에 표시하므로 대표 문장에 회사 이름을 주어로 억지로 넣지 않는다. 업종은 업무·어휘로 드러내고, 대표 문장은 그 회사 직원이 상사·동료·거래처에게 실제로 하는 말로 쓴다.
- 목록의 [Y1-10], [Y2-9·추정], [Y3-4], [Y4-12], [보충], [격식] 표시는 내부 정보로, 학습자 화면에 보이지 않는다. "문형" 줄을 포함해 응답 어디에도 붙이지 않으며, 표현 연습 화면은 안전장치로 이 형태의 표시를 화면에 그리기 전에 지운다(meta.ts의 stripSourceTags, 이메일 첨삭의 [담당자명] 같은 자리표시는 건드리지 않음).
### 1단계 출력 형식
- 첫 줄: "1단계: 표현 소개 (세트 N · 업종)"
- 각 표현은 "대표 문장 먼저, 문형 설명은 그 아래" 순서:
  1. [대표 문장]
  - 번역 / 사용 장면
  - 문형: [품사 표기 + 형태] (예: V-느라(고), V-(으)ㄹ 예정이다, N와/과 관련하여)
    · 기능(문법 용어 없는 쉬운 한 문장) · 만들기(초급 1개, 중·고급 2개) · 더 보기(같은 문형의 다른 직장 문장 1개, 길이 제한 동일) · 주의(중·고급에서 학습자가 자주 틀리는 형태·결합 제약이 있을 때만. 일반 말하기 조언이나 기능 줄 반복은 쓰지 않음. 예시 제약은 해당 문형에만 적용하고, 확실하지 않으면 생략. 초급 생략, "-(으)ㅂ시다"만 예외)
- 대표 문장: 마침표(또는 물음표)까지 갖춘 완성 문장으로 그대로 따라 말해도 되는 문장. 높임은 위 난이도별 높임 규칙을 따른다. 자기 이름·직책에는 '-님'을 붙이지 않는다("저는 과장님입니다" × → "저는 김민수 과장입니다" ○). 이 규칙은 서버 안내 끝에도 넣는다. 제목 줄과 문형 부분에 ** 굵게 표시를 쓰지 않는다(화면이 제목 전체를 강조). 프롬프트의 문형 목록에는 형태와 출처 표시만 넣고 예시 문장은 넣지 않는다(금지 목록에 넣어도 모델이 그대로 베껴 써서 제거). 예시 문장은 patterns.ts 데이터와 docs/level-guide.md에 교사용으로만 남긴다. 서버 안내에도 예시 문장을 넣지 않는다.
- 초급: "· 기능" 바로 아래 줄(공백 4칸 들여쓰기)에 영어 설명 한 줄.
- 화면: 표현 연습 응답의 "1. …" 번호 줄은 굵은 글씨 + 왼쪽 강조선 제목으로, "  · …" 줄은 한 단계 들여쓴 하위 목록으로, 공백 3칸 이상 들여쓴 줄은 하위 항목의 이어지는 줄로 표시한다(FormattedMessage의 numberedTitles 옵션, 표현 연습 탭에서만 사용).
- 마지막 안내문: "퀴즈 시작" → 지금까지 배운 표현으로 퀴즈 풀기 / "다른 표현" → 같은 주제의 새 표현 3개 더 보기 (초급은 영어 병기)
### 2단계 출제 규칙
- 퀴즈 문장은 대표 문장 또는 "더 보기" 문장을 그대로 쓰는 것을 우선하고, 난이도별 길이 제한을 지킨다. 빈칸은 1개, 목표 문형이 들어간 어절 하나(예: '끝난 후에'처럼 두 어절이면 "회의가 끝난 ____ 보고할게요."처럼 나누지 말고 "회의가 끝난 후에 ____."로 출제하거나 목표 어절이 하나로 떨어지는 문장을 고른다). 힌트는 10어절 이내. 들어갈 수 있는 적절한 표현은 여러 개일 수 있으며, 채점 단계에서 화용적으로 적절한 다른 표현도 인정한다. 힌트 규칙(정답 비노출, 초급 영어/중·고급 한국어)은 그대로.
### 3단계 채점
- 12장 기준으로 4단계 판정. 출력(중·고급): 결과 / 내 답 / 목표 표현(빈칸에 들어갈 활용형) / 완성 예문(퀴즈에 쓴 문장 전체 + 영어 번역) / 판단 근거(대상·높임, 장면·기능) / 뉘앙스 비교(다른 답일 때만) / 다음 안내. 초급은 각 줄 아래 영어 병기, 판단 근거 1~2줄.
- 기대 동작(회귀 세트): "팀장님, 어제 진행한 고객 설문 결과를 ____."(목표: 보고드리겠습니다) → 말씀드리겠습니다는 ✅(다른 적절한 표현), 말하겠습니다는 🟡, 여쭙겠습니다는 ❌ / 초급 "팀장님, 내일 다시 ____." → 이야기합시다 🟡, 이야기할까요 ✅. 프롬프트 안의 판정 예시는 이 문항과 다른 중립 문항("과장님, 오늘 교육 내용을 ____.")을 쓴다.
- 🟡·❌일 때만 [[NOTES]] 1개(original=학습자 답, corrected=목표 표현, scene="<주제> 표현 연습", counterpart=퀴즈 문장의 듣는 사람). 화면에서는 숨기고, 롤플레이·이메일과 같은 체크박스 저장 UI를 보여 준다(source 'expression').
### 빠른 응답 버튼
- 첫 표현 소개 응답이 끝난 뒤부터 입력창 위에 [📝 퀴즈 시작] [➕ 다른 표현 더 보기]. 누르면 "퀴즈 시작"/"다른 표현"을 그대로 전송(직접 입력과 동일). 스트리밍 중 비활성화, 대화 초기화 시 숨김. quick-chip 스타일 재사용.

## 12. 공통 화용론적 4단계 판정 기준 (표현 연습 채점·복습 채점 공용)
- api/_lib/level-rules.ts의 PRAGMATIC_GRADING_RULES 상수 하나로 정의하고 표현 연습·복습 채점 프롬프트에 끼워 넣는다(문구 중복 금지, 해설 원칙은 EXPLANATION_PRINCIPLES를 포함).
- 판단 축: ① 문법성(조사·어미 연결, 목적어–서술어 호응) ② 기능 일치 ③ 대상 적절성(높임·겸양) ④ 장면·격식. 띄어쓰기·문장부호는 반영하지 않는다.
- 판정: ✅ 정답(목표 표현 그대로, 활용형 포함) / ✅ 정답(다른 적절한 표현)(4가지 축 모두 충족, 뉘앙스 차이 1줄) / 🟡 부분 정답(기능은 맞지만 높임·격식·완곡함 부족, 또는 철자만 틀림) / ❌ 오답(문법 호응 안 됨 또는 기능이 다름). 애매하면 부분 정답 쪽.
- 난이도 고려(난이도 정보가 있을 때): 아직 배우지 않은 문형을 정답 조건으로 요구하지 않는다. 초급은 상사에게 해요체로 공손하게 말했으면 정답 또는 정답(다른 적절한 표현)으로 인정하고 하십시오체는 "더 격식 있게 말하려면 …"으로만 덧붙인다. 해설·힌트도 같은 수준(힌트 10어절 이내). 기존 판정 예시(보고드리겠습니다 등)는 고급 기준 예시. 상사 한 사람에게 "-(으)ㅂ시다"를 쓰면 🟡 부분 정답("-(으)ㄹ까요?"로 바꾸라고 안내), 회의 진행 장면에서 여러 사람에게 쓴 경우는 정상 채점.
- 해설: 근거는 듣는 사람·장면·기능으로. 문화 범주 단정 금지. 다른 적절한 표현을 틀린 것처럼 말하지 않고 "이 장면에서는 목표 표현이 더 ~하게 들린다"처럼 비교한다.

## 13. 롤플레이 도움 사다리 (💡 방향 힌트 · ✏️ 문장 틀 · 🔘 보기 선택 · 👀 모범 답)
학습자가 필요할 때 암시적인 도움에서 구체적인 도움 순서로 꺼내 쓰는 4단계 도움. 기존 롤플레이 흐름(장면 → 난이도 → 대화 → [피드백 받기] → NOTES 저장)은 그대로다.

### 13-1. 초급 롤플레이
- 난이도 [초급] 추가. 첫 대사는 scenes.ts(src·api 양쪽)의 openingLineBeginner(예: report-progress "행사 준비는 어때요?").
- 상대역 말하기 규칙(ROLEPLAY_LEVEL_RULES = 공통 LEVEL_RULES + 난이도별 문형 범위(patterns.ts로 생성) + 롤플레이 전용 규칙, 상대역·도움 코치·피드백 공용): 초급 1~2문장·문장당 5어절·해요체·1·2권 문형(목록 밖 중급 문형 예: -(으)ㄹ게요·-겠습니다·-(으)ㄹ 거예요·-고 있다·-군요·N 때문에는 금지, '-(으)니까'는 2권 문형이라 허용하되 '죄송·감사' 앞에는 쓰지 않음, '-(으)ㅂ시다'는 회의 진행자가 여러 사람에게만, 앞으로 할 일은 '-(으)ㄹ게요'·'-겠습니다' 대신 현재형(-아/어요), 초급 상대역도 장면 설정의 중급·고급 낱말을 초급 어휘로 바꿔 말함, 한자어 명사 겹침 금지(장면 설정의 겹친 명사는 핵심 낱말 하나로 줄임, '회사·업종 + 직원'은 예외). 서버 장면 데이터에는 선택 항목 situationBeginner(초급용 상황 문구)를 둘 수 있고, 난이도가 초급이면 상대역·도움 프롬프트가 이 문구를 씀(api/_lib/scenes.ts sceneSituation, 현재 colleague-request: '재무팀에서 자료를 받아야 함. 상대도 지금 바쁨', report-delay: '보고서가 늦어짐. 자료가 늦게 와서 다음 주 화요일에 낼 수 있음'). 선택 항목 learner(학습자 쪽 정보)는 상대·도움 프롬프트에 "학습자(나)"로 들어감(현재 client-postpone: '미래전자 영업팀 직원 (한빛상사의 거래처 담당자)'). 도움 프롬프트는 상대역의 회사·이름·직책을 학습자의 것으로 쓰지 않게 하고, 빈칸은 낱말 전체 자리(숫자 단위 제외)로, 순서를 바꾼 partial 보기도 자연스러운 문장으로, 문장부호만 바꾼 보기는 만들지 않게 함. 화면은 "{{n}}요일"을 "{{n}}"으로 고쳐 쓰고, 초급 범위 점검에서 '하지만요.'·'혹시요.'처럼 접속어·쿠션어만 남은 문장을 실패(level)로 봄, 예시 문장은 두지 않음)·초급 어휘 / 중급 1~2문장·7어절·3권 / 고급 1~3문장·8어절·4권. 시각 표현과 '-(으)ㄹ 수(도) 있다'·'-고 있다'·'N 중이다'는 한 어절.
- 초급 상대역 말 점검(화면): 상대역 응답이 끝나면 meta.ts beginnerReplyIssues로 검사한다(괄호 안 안내 제외, 최대 2문장("네." 같은 한 마디 제외)·문장당 5어절, 3권 이상 문형 '-군요'·'-겠-'(알겠습니다 제외)·'-(으)ㄹ게요'·'-고 있다'·'-(으)ㄹ 것 같다'·'-(으)ㄹ 거예요'·'때문에', 학습자가 먼저 쓰지 않은 중급·고급 명사, 금지 어휘). 걸리면 말풍선을 비우고 같은 기록에 simplify: true를 붙여 1회 다시 받는다. 서버는 simplify를 초급 롤플레이에서만 true로 받고(아니면 400), instructions 끝에 고정 문구 "[다시 말하기 (서버 안내)]"만 붙인다(금지 명사 목록은 적지 않고 "뭐가 좋아요?", "다른 것도 있어요?" 같은 쉬운 질문 꼴을 알려 줌). 다시 받은 말이 문제가 같거나 적으면 그것을, 더 많으면 처음 말을 보여 주고(chatState.pickBeginnerReply), 다시 받기에 실패하면 처음 말을 그대로 둔다. 다시 받는 동안 도움 패널은 열리지 않는다. 피드백 응답은 검사하지 않는다. 화면의 위 단계 명사 목록은 level-rules.ts VOCAB과 같아야 하며 테스트가 확인한다.
- 초급 피드백: 모든 줄 아래 영어 병기, "다시 생각해 볼 표현" 최대 2개. '-ㅂ/습니다' 평서형은 초급에서도 허용하므로 지적하지 않는다. 피드백의 "더 알맞은 표현"과 "다음에 써 볼 한 문장"도 학습자 난이도의 말하기 규칙을 지킨다(초급은 5어절 이하 1문장, 초급 어휘). "다음에 써 볼 한 문장"은 "말하기 순서 점검"에서 빠졌다고 짚은 단계를 연습하는 문장으로 쓰고, 이미 말한 내용은 다시 제안하지 않는다.

### 13-2. API: mode "roleplay_support"
- 요청: { mode: "roleplay_support", sceneId, level: "초급"|"중급"|"고급", supportType: "hint"|"frame"|"choices"|"model"|"starter", messages }. starter는 초급 전용(문장 틀 + 보기 선택을 한 번에).
- 검증(400 + 한국어 오류): mode·level·supportType 화이트리스트, starter는 초급만, sceneId는 SERVER_SCENES, messages 1~40개·메시지당 4,000자, 마지막 메시지는 assistant.
- 조립: instructions = ROLEPLAY_SUPPORT_PROMPT + 서버 장면 설정 + level + supportType(모두 서버 화이트리스트 값). input = messages + 서버가 만든 요청 메시지 "[도움 요청] 종류: {supportType} / 난이도: {level}" / "[지금 대답할 상대역의 말] {마지막 assistant 메시지}" / "[학습자가 이미 말한 내용] {학습자 발화를 ' / '로 연결, 없으면 '없음'}". 상대역의 말·학습자 발화는 서버가 messages에서 직접 뽑아 input에만 넣고 instructions에는 넣지 않음. 프롬프트는 [지금 대답할 상대역의 말]에 대한 대답만 돕고(첫 질문·장면 목표 전체 금지), 이미 말한 사실은 전제로 삼아 다시 말하게 하지 않으며, 장면에 없는 세부 사실(이유 등)은 frame에서는 빈칸으로, choices·model에서는 그럴듯한 사실 하나를 정해 세 보기에 똑같이 씀. JSON 예시는 앱 장면에 없는 중립 상황(동료의 "점심 먹고 회의할까요?")이며 형식 참고용.
- 응답: 기존 SSE. 출력은 [[SUPPORT]]{ JSON }[[/SUPPORT]] 하나(hint: steps 2~3개·steps_en / frame: template의 {{n}}과 blanks id 일치·빈칸 1~3개·내용어 자리만·빈칸 하나에 내용어 하나(조사는 함께 가능)·빈칸 바로 뒤에 받침에 따라 바뀌는 조사(이/가, 을/를, 은/는, 과/와) 금지("{{n}}이/가"·"{{n}}(이)"처럼 두 형태를 적는 것도 금지; 조사까지 빈칸에 포함. 모델이 어기면 화면이 고쳐 씀: 틀에서 그 조사를 빼고 해당 빈칸 힌트에 "+ 이/가"·"+ 을/를"·"+ 은/는"·"+ 과/와"를 붙임. 고친 뒤에도 빈칸이 문장 끝이면 실패)·빈칸을 문장 끝에 두지 않음(빈칸 뒤에 항상 서술어; 화면 검증도 실패 처리)·숫자 빈칸은 단위(%, 시, 일 등)를 빈칸 바로 뒤에 붙여 둠(학습자는 숫자만 씀)·빈칸 hint는 들어갈 말의 종류를 구체적인 명사구로("무엇인지"·"어디인지"처럼 묻는 꼴 금지), 조사 안내는 모델이 쓰지 않고 화면이 정함(meta.ts normalizeBlankHint: 모델이 쓴 조사 안내는 지우고, 빈칸 바로 뒤에 '있다/없다'가 오면 "+ 이/가"를 붙임. 단 힌트가 숫자·개수를 가리키면 붙이지 않음). 정답 단어는 중급·고급 hint에 쓰지 않고, 초급은 떠올리기 어려우면 보여도 됨 / choices: 보기 3개·verdict appropriate·partial·inappropriate 각 1개·오답 보기도 장면 사실은 그대로 두고 높임·말투·완곡함·보고 순서 중 하나만 틀리게 / model: text·tip, 두 문장이면 끝맺음 말투 통일('-ㅂ/습니다'와 '-아/어요'를 섞지 않음) / starter: frame + choices). 초급은 *_en 필드(text_en·tip_en 포함)를 하나도 비우지 않고 중·고급은 비움. *_en 필드에는 한글을 쓰지 않음(화면은 섞여도 실패로 보지 않고 개발 모드 콘솔에만 기록, 화면이 붙이는 "+ 이/가" 안내는 제외). 설명(reason·tip·hint)에는 문법 용어(해체, 하십시오체 등) 대신 '반말', '높임말' 같은 쉬운 말을 쓴다.
- OpenAI 한도 초과(429)는 429 상태로 그대로 전달한다(화면이 "잠시 후 다시 시도"를 보여 주도록).

### 13-3. 화면 (src/components/RoleplaySupportPanel.tsx)
- 입력창 바로 위. 초급은 상대역 말이 끝날 때마다 starter를 자동 1회 요청해 ✏️·🔘를 펼쳐 보이고 💡·👀는 버튼. 중급은 [💡 도움]을 누를 때마다 다음 단계가 하나씩 열림(열린 단계는 계속 보임). 고급은 같은 동작을 작은 링크 "도움이 필요하면 누르세요"로.
- ✏️ 빈칸 입력칸 + 회색 hint, 다 채우면 [입력창에 넣기]. 🔘 보기는 화면에서 무작위로 섞고, 고르면 ✅/🟡/❌ + reason, appropriate일 때만 [입력창에 넣기], 두 번 틀리면 정답 강조. 👀 text·tip + "읽어 본 뒤 내 말로 바꿔 말해 보세요." [입력창에 넣기]는 자동 전송하지 않고 입력창에 넣고 포커스만 옮김.
- 응답 공통 필드: 모든 type에 replyTo(대상 상대역 발화 복사, 필수·비어 있으면 검증 실패)·intent·intent_en(초급만 채움). starter는 최상위에 한 번. 화면은 패널 맨 위에 "지금 할 말: {intent}"(초급은 영어 병기)를 작게 표시.
- replyTo 검증: "[난이도: …]" 표시·공백·문장부호·따옴표를 지우고 비교. 전체가 같거나, 한쪽이 다른 쪽을 포함하거나, replyTo가 상대역 발화의 문장 하나와 같으면 일치(meta.ts replyToMatches).
- starter 틀-정답 검증: 정답 보기가 문장 틀을 채운 문장과 같은 구조가 아니면 실패(schema). 같은 구조면 정답 보기의 빈칸 값 끝 조사(에·에서·까지·부터·에게·한테)를 틀에 옮겨 적음(alignFrameWithAnswer).
- 빈칸 기호 검증: {{n}}은 frame.template 안에서만 허용. 그 밖의 문자열 필드(보기·힌트·모범 답·intent 등)에 있으면 실패(placeholder). 보기 문장이 똑같은 것이 둘 이상이어도 실패(schema). 프롬프트도 choices는 완성 문장, frame 빈칸 내용은 구체적인 예시 하나로 세 보기에 똑같이, 세 보기는 같은 사실을 다른 방식으로(문장은 서로 다르게), 초급 보기는 최대 2문장·문장당 5어절 이하로 쓰게 함(장면 목표의 단계가 많아도 꼭 필요한 단계만 2문장에 담고 근거 등은 뺌. 반대 의견 장면 초급은 '인정' 한 문장 + '하지만'으로 시작하는 대안 한 문장. 일정 지연·문제 보고 장면 초급은 결론 한 문장 + 새 일정·대책 한 문장(원인은 상대역이 물을 때). 이 구조는 상대역이 제안에 대한 생각·다른 의견을 물을 때만 쓰고, 이유·방법·비용 같은 구체적인 질문에는 '하지만' 없이 바로 대답). 초급 범위 점검에서 문장 틀·보기·모범 답이 2문장 초과("죄송해요."·"안녕하세요."·"네." 같은 한 마디 인사·사과·대답은 세지 않음)이거나 문장당 5어절 초과면 실패(level, 어절 셈은 docs/level-guide.md 1-2 기준).
- 초급 범위 점검(meta.ts beginnerSupportIssue, 초급에서만): 문장에 'N 때문에·-기 때문에'나 '죄송·감사' 앞의 '-(으)니까'가 있거나, 위 단계 명사(BEGINNER_BANNED_NOUNS, 예: 예약)가 있거나, 끝맺음이 '-ㅂ/습니다'인 오답 보기의 reason이 말투(딱딱함·격식 등)를 탓하면 실패(level). 프롬프트도 초급 이유는 이유 문형 없이 짧은 문장으로 따로 말하게 하고, 초급 partial 보기는 순서 바뀜·정보 하나 빠짐·인정 없이 바로 반대 중 하나로만 만들게 함.
- 추가 점검(모든 난이도): 문장 틀·정답 보기·모범 답이 학습자가 이미 말한 문장(6자 이상)을 그대로 넣으면 실패(repeat), 한 보기 안에 같은 문장이 두 번이면 실패(schema). 중급·고급은 문장당 최대 어절(7·8) 초과면 실패(length)지만, 1회 재요청 뒤에도 길이만 넘으면 버리지 않고 보여 줌(meta.ts supportLengthIssue·repeatsLearner). 빈칸 뒤 고정 조사 보정에 '로/으로'(힌트 "+ (으)로")도 포함. 중·고급 hint의 steps_en은 없거나 빈 배열이어도 받음.
- 실패 분류와 재요청: http / level / repeat / length / truncated(닫는 [[/SUPPORT]] 없음 또는 괄호 불균형, 마커 없이 끊긴 JSON 포함) / parse / schema / placeholder / replyTo. placeholder·replyTo·level·repeat·length 실패와 frame·choices의 schema 실패는 자동으로 한 번 다시 요청하고, starter는 모든 실패를 한 번 다시 요청. starter가 2번 연속 실패하면 frame과 choices를 따로 1번씩 요청해 합침(대체 경로, 1회; choices 요청에는 먼저 받은 문장 틀을 frameTemplate으로 보내 정답 보기를 그 틀에 맞춤). 단, starter 첫 실패가 문장 틀의 빈칸 개수 오류나 빈칸이 문장 끝인 오류면 재요청 없이 바로 대체 경로로 감. 프롬프트는 빈칸을 명사 자리(날짜·요일·시간·이름·물건·장소·숫자)에만 두고 서술어·인사·사과·대답말 자리는 틀에 적게 함. 그래도 실패하면 "도움을 불러오지 못했어요. [다시 시도]"([다시 시도]는 그때의 최신 대화 기록으로 다시 보냄). 실패하면 개발 모드에서 console.warn으로 분류·supportType·마지막 상대역 발화·응답 앞 300자를 남기고, 화면에는 서버 오류 원문을 보이지 않음. 서버에는 출력 길이 제한(max_output_tokens)을 두지 않음.
- 보기 선택 상태: 처음과 새 보기를 받을 때 선택 없음. 마우스를 올렸을 때는 배경만 살짝 바뀌고(선택처럼 보이는 파란 테두리 없음), 키보드 포커스 표시(:focus-visible)는 선택 상태 스타일과 분리.
- 요청 시점: 상대역 응답 스트리밍이 끝나고(done) 마지막 상대역 말이 비어 있지 않을 때만 패널을 마운트하고 starter·도움을 요청. 학습자가 말을 보내는 순간 패널을 비우고 다음 상대역 발화가 끝날 때까지 "다음 대답을 준비하고 있어요…"(초급은 영어 병기)만 표시. 도움 요청에 쓰는 대화 기록은 요청 직전에 ref로 최신 값을 읽고, 마지막 상대역 말이 패널 대상 발화와 다르면 보내지 않음. 개발 모드에서는 요청마다 마지막 상대역 발화를 console.debug로 찍음.
- 상태: 도움 결과 캐시 키는 "상대역 발화 순번 + 발화 텍스트 해시 + supportType"(같은 턴에서 다시 열면 API 재호출 없음). 새 상대역 발화가 오면 패널을 새로 마운트하고 이전 턴 캐시 항목을 지움. 스트리밍·도움 요청 중에는 버튼 비활성, 도움 요청은 한 번에 하나. 도움 요청·응답은 롤플레이 대화 기록에 넣지 않음. 장면 변경·새 시작·[피드백 받기] 이후 패널·캐시 비움, 피드백 뒤 패널 숨김.
- 파싱(meta.ts extractSupport): [[SUPPORT]] 블록(없으면 첫 "{"~마지막 "}"), 코드 펜스 제거, JSON.parse try/catch, 구조 검증. 실패하면 "도움을 불러오지 못했어요. [다시 시도]"(초급 영어 병기, 자동 재시도 없음). 429면 "잠시 후 다시 시도해 주세요." + 30초 비활성. 서버 오류 원문은 콘솔에만.
- 접근성: 버튼 aria-label, 키보드로 보기 선택·빈칸 입력. 375px에서 보기 3개는 세로로 쌓음.

### 13-4. 도움 사용 기록과 피드백
- 기록: 종류별 사용 횟수(턴마다 종류별 1회), 처음 고른 보기의 verdict, [입력창에 넣기]로 시작한 발화와 출처(frame/choices/model)·수정 여부(넣은 문장과 보낸 문장이 다르면 "수정함").
- [피드백 받기] 때 전송용 사용자 메시지 끝에만 "[도움 사용 기록]" 블록을 붙인다(말풍선·instructions에는 넣지 않음, 사용 기록이 없으면 붙이지 않음, src/utils/supportUsage.ts). 학습자 발화가 모두 도움 문장을 그대로 보낸 것이면 기록 끝에 "직접 쓴 발화: 없음 (잘한 점에 발화를 인용하지 말 것)"을, 아니면 "직접 쓴 발화: N개"를 덧붙인다(프롬프트는 "없음" 줄이 있을 때만 생략 규칙을 적용).
- 롤플레이 피드백 규칙: 기록이 있으면 "잘한 점" 다음에 "### 도움 사용" 1~2줄, 나무라지 않고 다음 목표 제안, 도움 문장을 그대로 보낸 발화는 "잘한 점" 근거로 쓰지 않음(고친 부분은 칭찬 가능), NOTES에는 학습자가 직접 쓴 발화의 문제만. 학습자 발화가 모두 "그대로"이면 잘한 점은 도움을 활용해 말을 시작한 점만, "다시 생각해 볼 표현"은 "직접 쓴 발화가 없어서 이번에는 생략해요." 한 줄, NOTES는 빈 배열.

## 14. 공통 기준·검증 체계 (자동 정비로 추가)
- 단일 기준: api/_lib/level-rules.ts에 LEVEL_RULES(문법 범위·문장 길이·문체 표, 어절 세기, 어휘·명사 겹침·금지 어휘, '-(으)ㅂ시다'), PRAGMATIC_GRADING_RULES, EXPLANATION_PRINCIPLES, EXAMPLE_POLICY(예시는 그대로 복사하지 않음), INTERNAL_MARKER_RULE을 둔다. 표현 연습·롤플레이·롤플레이 도움·복습 채점·이메일 프롬프트가 모두 끼워 쓰고, 같은 규칙을 프롬프트마다 따로 적지 않는다(tests/server.test.ts가 각 프롬프트에 한 번씩 들어가는지 확인).
- 내부 표시 제거: 모든 탭의 화면 표시는 cleanDisplayContent → stripInternalMarkers로 "[난이도: …]", 출처 표시([Y1-10] 등), 전송용 블록([이미 소개한 문형]·[이미 쓴 대표 문장]·[도움 사용 기록]·[서버 안내])을 지운다. 이메일 자리표시([날짜] 등)는 남긴다.
- 표시·전송 분리: 표현 연습의 화면 인사말은 API로 보내지 않는다(chatState.buildExpressionPayload). 새 메시지를 보내면 이전 채점의 노트 저장 후보를 지운다. 모든 전송 버튼은 ref 가드로 중복 전송을 막는다.
- 자동 테스트: npm run test (Node 내장 node:test, 의존성 추가 없음, scripts/ts-register.mjs가 .ts import를 해석).
- 실제 응답 검증: node --import ./scripts/ts-register.mjs scripts/eval.mjs [--groups=A,B,C,D,E] [--ids=…]. 원문은 eval-out/(gitignore), 결과는 docs/eval-report.md. 호출 간격 3초, 누적 80회 한도.
- 개발 전용 가짜 응답: 개발 서버에서 ?mock=1을 붙이면 API 없이 각 탭 흐름을 확인할 수 있다(src/api/mockChat.ts, 배포 빌드에서 제거됨).
